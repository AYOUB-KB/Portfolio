A simple question about Pthreads that made me think differently about IT

So recently I was curious about C, and I decided to start a small course just to become a little bit more familiar with the language.

At some point, I arrived at Pthreads.

Pthreads are related to POSIX Threads and basically allow a program to have multiple threads running concurrently inside the same process.

At first, I understood it in a very simple way.

Multiple tasks can run at the same time.

Without threads Task 1 Task 2 Task 3 With threads Thread 1: Task 1 Thread 2: Task 2 Thread 3: Task 3

Cool.

But then I asked myself something.

Wait... if I create multiple threads, doesn't that affect the RAM?

And honestly, that question is what made me write this article 😂

Because after asking that question, I started questioning the question itself.

Why did I ask that?

And then I realized that I sometimes do this naturally when learning IT.

Someone explains a technology and tells me how to use it.

But my brain sometimes goes:

Okay... but what happens if I actually use it?

Not just, does it work?

But what else does it affect?

And I think this way of thinking is something really interesting in IT.

I'm definitely not an expert, by the way. There are probably people with much more experience than me reading this. I'm mostly writing this to share my thoughts and also to keep track of what I'm learning.

It's not only about Pthreads

My original question was about RAM and threads. But then I realized that the same logic can be applied almost everywhere in IT.

Let's imagine you're a System Administrator.

You have a simple objective. You want to block port 80 in the firewall.

You do it.

Firewall rule Block port 80

The rule works.

Mission accomplished, right? 🎉

Well... maybe.

As a beginner, I think it's easy to only look at the direct result.

I wanted to block port 80.

Port 80 is blocked.

Great.

But then you can start asking other questions.

What did I actually change?

I blocked port 80 in the firewall.

Simple.

But a firewall rule is part of a bigger system.

So now the next question becomes, what is using this?

Web server? Reverse proxy? Monitoring? Users? API? Other services?

Maybe blocking port 80 does exactly what you wanted.

But maybe something else was depending on it.

What depends on it?

Sometimes the problem isn't directly visible.

Service A depends on Service B depends on Service C

You change something in Service A.

Then Service C suddenly stops working.

And you're thinking, wait... I didn't even touch Service C.

But that's exactly the point.

Systems are connected.

One thing can affect another thing indirectly.

What could go wrong?

Another question I think is useful is, what's the worst-case scenario?

Website inaccessible? Production service broken? Users can't connect? Monitoring stops working? Remote access lost?

I'm not saying we should be scared to make changes.

Otherwise, we would never touch anything 😂.

But understanding what could happen before making a change seems like a good habit.

And how do I go back?

This is another thing I think about.

Something goes wrong. Can I undo it? Do I have a backup? Do I have a rollback plan?

Sometimes the change itself is easy.

The difficult part is recovering when something unexpected happens.

So what does this have to do with Pthreads?

Let's go back to my original question.

Will Pthreads affect RAM?

Someone tells you that threads allow multiple tasks to run concurrently.

Okay.

But then you can start asking yourself more questions.

What happens if I create one thread? What about 10? 100? 1,000? 10,000?

Then more questions start appearing.

Does every thread use memory? How much memory? What happens to the CPU? How does the operating system manage them? What happens if there are too many? Do the threads share data? Can they interfere with each other? Can something break?

And that's basically the connection I was thinking about.

The question isn't only how do I use this?

It's also, what happens when I use this?

And maybe, what else can this affect?

The mindset I'm trying to develop

I don't know if there is one perfect name for this.

Maybe it's related to Systems Thinking.

Maybe it's Critical Thinking.

Maybe it's thinking about dependencies.

Maybe it's thinking about consequences and implications.

Probably a mix of all of them.

But the general idea is simple.

When I'm learning something new in IT, I want to start asking myself questions.

What does this actually do? What does it change? What resources does it use? What depends on it? What can be affected? What are the limits? What could go wrong? What happens if I scale this? How can I recover if something breaks?

Of course, you don't need to overthink absolutely everything.

You don't need to make a complete analysis before doing something simple 😂.

But when you're working with systems, networks, servers, security, or programming, I think these questions can become really useful.

Final thought

This whole article started with a very simple question.

Will Pthreads affect RAM?

And somehow, that small question made me think about something much bigger.

When learning IT, I don't only want to know what something does.

I also want to know what happens behind it.

What are the consequences?

What else could this affect?

Maybe that's Systems Thinking.

Maybe it's Critical Thinking.

Maybe it's just asking better questions.

I don't know yet.

But I think it's a habit worth developing.

Don't only learn how to use something. Try to understand what happens when you use it.
